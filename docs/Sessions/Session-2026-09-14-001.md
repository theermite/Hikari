## 5. Leçons

**Objectif** → livrer le chat (trois parties) et le publier sur la version installée.
**Processus** → TDG suivi sur chaque partie (tests avant code) · veille datée sur chaque
nouvelle dépendance/scope (11 marqueurs) · commits atomiques · défi technique posé avant de

**Résultat** → les trois parties du chat livrées, testées, publiées et confirmées à l'écran
par Jay ; le spike de superposition a échoué et a coûté, avec le nettoyage qui a suivi,
près de trois heures de la session.

### Leçon 1 — Un processus tué n'est pas un processus mort, sur cette machine

Cinq incidents distincts cette session (fenêtres dupliquées, blocages de compilation
identiques, cache corrompu) partageaient TOUS la même racine : `taskkill` ou l'arrêt d'une
tâche en arrière-plan ne tue pas fiablement les processus enfants (`cargo`, `node`,
`rustc`) qu'elle a lancés. Le signal qui aurait dû alerter plus tôt : plusieurs blocages
identiques au même point exact, jamais aléatoires. La leçon : après tout arrêt forcé sur ce
projet, vérifier par la LIGNE DE COMMANDE complète (jamais le seul nom du processus) qu'aucun
enfant n'a survécu — avant de relancer, pas après le deuxième blocage.

### Leçon 2 — Un test isolé bat une heure d'hypothèses sur l'environnement

Trois hypothèses ont été explorées avant de trouver la vraie cause du dernier blocage
(pilote graphique, profil WebView2, cache de compilation) — seul un test dépouillé de toute
couche (`cargo build` seul, sans `tauri dev`, sans processus enfants superflus) a permis de
trancher en moins de deux minutes que le CODE n'était jamais en cause. Mesurer avec le
chemin le plus court bat empiler les hypothèses plausibles — la même leçon que celle
retenue le 2026-09-08 sur l'écran blanc de l'époque, jamais généralisée jusqu'ici à « toute
la chaîne de compilation », pas seulement à la fenêtre.

### Leçon 3 — Une scène de test parle encore après que le code qui l'a créée a disparu

Le spike retiré du code a laissé une scène « Spike Overlay » dans la session PERSISTÉE de
Jay — parce que Hikari sauvegarde son état à chaque changement, indépendamment du code qui
l'a produit. Retirer un correctif du dépôt ne retire pas ce qu'il a déjà écrit sur le disque
de l'utilisateur. Un spike qui touche l'état persisté doit être annoncé comme tel avant
d'être lancé, pour que son retrait soit aussi complet côté disque que côté code.
