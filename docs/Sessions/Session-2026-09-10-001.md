## 4. Décisions prises

| Décision | Motif |
|---|---|
| **La relance d'une caméra appelle le gestionnaire de procédure natif de win-dshow**, jamais une reconfiguration de réglages | C'est le mécanisme qu'OBS lui-même utilise pour ce geste ; une reconfiguration ne déclenche jamais le signal « plus d'image » |
| **La décision de retry vit dans une fonction pure, hors du crate `engine`** | `engine` n'a aucun test (`test = false`) ; une machine à états qui a produit plusieurs FAIL ne se fiabilise qu'en devenant testable |
| **Un abandon ne parle que si une tentative a réellement eu lieu** | Accuser une caméra jamais mise à l'épreuve est un mensonge pendant un direct |
| **Les formes d'onde animées de la maquette ne seront pas construites** | Décision de Jay — la barre de niveau simple actuelle suffit |
| **3 points d'alignement maquette retirés de la liste « restants »** | En-têtes de cartes, ligne Transition et œil montrer/cacher sont déjà faits — la documentation était en retard sur le code |

### Leçon 1 — Un contournement qui devine un état ne suffit pas quand on peut lire le signal réel

Les tours 6 et 7 ont chacun ajouté une défense côté Hikari (réessayer, comparer deux
lectures) contre un comportement de libobs mal compris. Les deux ont rouvert la même
famille, parce qu'ils devinaient une stabilité au lieu de la mesurer. La veille qui a
tranché — lire le code source réel de `obs-source.c` et de `win-dshow.cpp` — a montré que
libobs expose déjà le signal exact dont le code avait besoin (`async_active`, remis à faux
par un appel de procédure que le plugin enregistre lui-même). Une fois ce signal utilisé
directement, plus aucun contournement n'a été nécessaire.

### Leçon 2 — Huit tours sur une brique interrogent la méthode, pas seulement le code

`Independent-Review.md` prévoit l'arrêt au deuxième FAIL consécutif sur la même famille, et
cette règle a joué deux fois dans cette session (tours 2→3, puis 6→7). Chaque fois, la
question posée à Jay a été concrète et fermée — deux chemins nommés, un choix à faire —
jamais une reprise automatique d'un troisième essai. Le coût mesuré (8 relectures) est réel,
mais chaque tour a trouvé un défaut qu'aucun test vert n'aurait attrapé avant l'écran de Jay.

### Leçon 3 — Une note de projet vieillit plus vite que le code qu'elle décrit

3 des 5 points notés « restants » sur l'alignement maquette étaient en réalité déjà livrés,
certains depuis plusieurs sessions. La vérification ligne à ligne (code + maquette), demandée
par Jay plutôt que supposée, a coûté quelques minutes et corrigé une fausse dette affichée
depuis au moins une session.
